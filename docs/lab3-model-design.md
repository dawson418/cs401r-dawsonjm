# Lab 3 Model Design

**Track B (offer generation, RAG)**

## Churn model
NorthStar has about 10,000 customers and a handful of tabular features, with 22% churners. At that size a gradient-boosted tree model is the right tool: it captures interactions (for example, low category diversity combined with recent purchases) that logistic regression cannot without hand-built terms, and a neural network would have far more capacity than 7,000 training rows can support. Tree models also give gain importances and per-tier slices the retention team can read. I would switch if the input became raw event sequences (clickstream) at much larger scale, or if the business needed calibrated per-customer explanations at which point I would add SHAP on top of the same model.

## What the features bought
Recency-only baseline AUC was 0.7203; the full model reached 0.7846, a lift of 0.0643 with a 95% paired-bootstrap CI of [0.0446, 0.084]. The interval excludes zero, so the engineered features did measurable work, but the lift is modest, not transformative. The model leans most on days_since_last_purchase (23%), purchase_frequency_180d (16%), purchase_frequency_30d (12%). The weakest features by gain were category_diversity_score (5%), online_to_store_ratio (5%), customer_tenure_days (4%), and I treat those as close to decorative here. The weakest tier with enough data is **Silver** (AUC 0.7179, recall 0.2301, n=1139, 226 churners). Tiers too small to conclude from: Platinum. I excluded churn_risk_score from the graded model because it is a recency heuristic and would make the baseline comparison circular; I also ran it as a separate experiment to check.

## LLM system
I chose RAG over fine-tuning because NorthStar's policies (the 30-day return window, tier benefits) change, and a fine-tuned model would bake in a stale snapshot and could not cite which clause supports a claim. With RAG, an offer is traceable to retrieved chunk IDs and updating a policy means re-indexing a document, not retraining. The primary production risk is a faithfulness failure: promising a benefit the customer's tier does not carry. The feature store's loyalty tier is derived from lifetime value while policy defines tier by trailing 12-month spend, so near a threshold the two disagree. My system prompt only allows tier benefits that appear in retrieved policy text, and falls back to generic wording otherwise. In production the tier should be read from the system of record at generation time.

## What I would do differently with 10x time or data
I would replace the LLM-judged scores with a deterministic claim checker that extracts every number, deadline and benefit from an offer and verifies each against the policy corpus, run on hundreds of generated offers instead of four test cases. For the churn model I would validate on a true temporal split across several cutoff dates instead of a single random split, and move from predicting churn to modeling uplift so the retention budget goes to customers an offer can actually change.

## Supporting detail
Three configurations varied depth and learning rate: depth 3 / eta 0.1 reached AUC 0.7785, depth 6 / eta 0.1 reached 0.7796, and depth 4 / eta 0.05 reached 0.7846, which became the graded model. Deeper trees overfit fast: the depth-6 run early-stopped at iteration 11, while depth 4 with a lower learning rate ran to iteration 97. Adding churn_risk_score moved AUC from 0.7846 to 0.7842, which is nothing, so it is redundant with days_since_last_purchase. scale_pos_weight was 3.54, the training-split ratio of non-churners to churners (about 22% churn). Precision@10% was 0.717 and recall@10% was 0.326; with 22% positives a 10% contact budget caps recall near 45%, so the model reaches about 72% of what is reachable. The slices show why one aggregate hides structure: global top-10% targeting is dominated by Bronze (33% churn, recall 0.43), while Gold (recall 0.12) and Platinum (only 21 test churners, too few to conclude from) are barely reached because their base churn rates are 11% and 8%. If the retention team wants coverage of high-value tiers, a per-tier budget or value-weighted ranking is needed.

## Limits of the prompt-only guardrail
Prompt instructions did not fully prevent unfaithful claims. In development the generator gave a Gold customer a Platinum-only 60-day return window, and in the RAGAS run it told a Bronze customer her points "expire in 14 days" by misreading a warning-window clause. Both phrases exist in the corpus, so a text-match lint passes them. The fix is claim-level verification against the specific chunk, and customer-specific state (tier, points-expiry date) read from the system of record instead of inferred.
